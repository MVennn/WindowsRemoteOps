# release-notes/

> **一句话**：面向使用者的 Release 说明模板与写法 —— 文件名 = 版本号（不带 `v`），
> 首行加粗总结、次行反馈入口、清单式正文、固定风险尾巴。

放**面向使用者**的 Release 说明，**文件名 = 版本号本身**（如 `0.1.0`），**不带 `v` 前缀** ——
`v` 前缀只属于发版 tag：

```text
docs/release-notes/0.1.0.md
```

版本号与 [CHANGELOG.md](../../CHANGELOG.md) 的段标题一致；打 tag 时把 CHANGELOG 的
`## [未发布]` 段改成 `## [版本号] — <日期>`，并把本目录下的同名文件作为 Release 说明。

## 为什么要单独放一份

`CHANGELOG.md` 是**开发者记录**：症状 / 根因 / 改法 / 验证结果 / 踩坑。
Release 说明是**给使用者看的**，要短、写成清单、只讲「我现在能拿到什么」。
两者受众不同，不能一份两用（见 [DOC-RULES.md](../DOC-RULES.md) §3 的单一正本原则）。

本仓的「使用者」是**要接管一台 Windows 主机的人** —— 他关心的是：
「跑哪条命令能开通、出事了怎么查、哪些坑别再踩」。

## 形状

**清单，不是文章。** 开头一句加粗概述，`## 本版内容` 下按分区一行一条，最后是固定尾巴。

**第一行必须是加粗总结；紧接的那一行是反馈入口**（一行，不是清单条目，链接用绝对地址），
然后才是 `## 本版内容`。

```markdown
**首版：把「Windows 主机开通 SSH」这件事整理成能照着做、能自己排错的仓库。**

遇到问题、想要新功能，到 [Issues](https://github.com/MVennn/WindowsRemoteOps/issues/new/choose) 反馈 —— 请附 Windows 版本、执行的完整命令、报错原文。

## 本版内容

**脚本**

- 新增 host/bootstrap-openssh.ps1 —— 目标机上跑一次，装能力、起服务、放行 22、写公钥。
- 新增 tools/verify-host.py —— 操作机上跑一条命令，四项验证一次过。

**文档**

- 新增 接入踩点 —— 四条路的取舍，以及为什么不该先去 GitHub 找远程控制项目。
- 新增 排错手册 —— 八个高频现象，各配可直接粘贴的排查命令。

---

需要 Windows 10 1809+ / 11，管理员权限。
`host/bootstrap-openssh.ps1` 会改目标机状态，执行前请先看 [架构与边界](../ARCHITECTURE.md) 的「会改什么」。

---

> 风险提示：开通 SSH 等于给这台机器开一个远程入口。请只在自己的机器与局域网内使用，
> 不要把 22 端口映射到公网；确认密钥登录可用后立刻关闭密码认证，
> 详见 [凭据与主机配置](../SECRETS.md)。
```

结尾那两行是**固定尾巴**，每版照抄不动（法律留痕：持续提示、提示在先），**不算重复内容**。

## 反馈入口：写在开头，链接必须是绝对地址

每份说明的**第二行**放一行反馈入口，不是清单条目：

- 链接写绝对地址 `https://github.com/MVennn/WindowsRemoteOps/issues/new/choose`
  —— 说明会被贴到 Release 页面，相对链接在那里解析不到；
- `issues/new/choose` 会先让用户选「问题反馈（Bug）」还是「功能建议」；
- 已发布的历史正文**不回填**；这条规则只对**新版本**生效。

### 一条怎么写

```text
新增 / 调整 / 修复 / 优化 + 对象名 —— 入口或位置；一句话你拿到什么
```

- **动词只有四个**：新增（以前没有）、调整（行为、默认值、位置变了）、
  修复（以前不对，含底层与实现层）、优化（你更能感知的更快 / 更小 / 更顺）；
  另有「移除」用于删功能。都写全称。
- **对象名照抄仓库里的实物**（文件名 / 文档名 / 脚本名）。
- **入口**写你找得到的位置：「仓库根 README」「docs/ 索引」；
  不需要找入口的（脚本、命令），改写场景（「目标机上」）。
- **一句话说完你拿到什么**。不写怎么用、不写为什么。
- 一行一条。两句才说得清 → 拆成两条。

## 覆盖率红线

**凡本版改过的东西，必须全部出现在 Release 说明里**，动词四选一，一行一条。没有例外：

- 脚本行为变化 → 并进「脚本」分组，一行写「改了哪 + 你能感知的后果」
- 文档新增 / 改名 / 删改 → 并进「文档」分组，照写
- 纯搬迁 / 纯重构（行为零变更）→ 并进「修复」分组，**按对象拆成多行**
- 默认值变化（如默认关闭密码认证）→ 并进「脚本」分组，**必须写**

写完拿 CHANGELOG 对应段落逐条对：**CHANGELOG 里的每一处用户可感知改动，
Release 说明里都得能找到对应行**。

## 别写这些

| 别写 | 为什么 |
|---|---|
| 第二人称叙述（「点一下就…」） | 用户要的是有什么，不是操作步骤；步骤归 README 与排错手册 |
| 「原来是这样，所以现在…」的原因与取舍 | 解释属于 CHANGELOG |
| 实现原理、脚本内部机制 | 同上 |
| 「之前是什么样」的对比 | 只有修复条目允许一句症状，其余不写 |
| 「本版没有破坏性变更」 | 没变更就不用声明；**有**的时候才必须写 |

## 「注意」区块：能不写就不写

只在**你不知道就会出问题**时才写，最多一两条：

- ✅ **有破坏性变更** —— 参数改名、默认行为反转。**必须写**。
- ✅ **已知的、会被当成新 bug 的问题** —— 如实写一条。
- ❌ 每版都一样的操作提醒 —— 不写。风险提示**例外**，属固定尾巴。
